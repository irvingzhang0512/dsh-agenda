# 年度节假日自动更新契约

文档版：`agenda-holiday-update-20261014-v1`；2026-10-14。目标：DSH Desktop `0.2.0-rc.2`。状态：待用户确认本版文档／待实现／未运行功能验收。

用户已选择“自动应用通过校验的官方数据；本地手改内容保留并提示冲突”。该选择确定应用策略，不代替对本版具体周期、接口和验收的确认。本契约补充 [SPEC F005、F008、F010](SPEC.md)，与此前 Desktop 适配一起实施；原始需求只读保留。

## 1. 任务与周期

- Agenda 内置一个宿主级“节假日更新”任务，所有窗口／会话共用。不创建会话、不调用模型，不依赖 dsh-automation 或官方 Schedule。目标版本 Schedule 的公开服务管理原会话提醒，未提供任意业务回调注册接口。
- 自动更新默认开启；唯一新增配置为 `holidayAutoUpdate: boolean`，与 `weekStart` 同属业务目录的 `settings.yaml`。在 Agenda 插件设置卡提供开关、中文说明及“立即检查”。旧配置缺字段时使用 true；保留旧 weekStart 和未知字段，不能整份覆盖 YAML 或复制到宿主全局配置。
- 时区固定 `Asia/Shanghai`。每年 10 月至次年 1 月，每日 09:00 检查；2–9 月每月 1 日 09:00 检查，以发现补充／更正安排。每次查询当年的公告数据，10–12 月同时查询下一年。
- 开启后首次挂载立即检查；以后持久记录检查时刻与下一次计划。Desktop 启动或休眠恢复时，如果计划已到期，只补一次最新检查，不重放错过的所有周期。关闭自动更新后不联网、不补跑，但“立即检查”仍可用。
- 任务仅在 Desktop 宿主运行时执行，不安装 Windows 计划任务，不承诺关机／退出后运行。并发的自动与手动检查合并为一次，跨进程使用业务目录锁避免同一目录重复写入；卸载取消请求并释放定时器。
- 网络错误保留原数据，在 1 小时后重试，同一日最多额外重试 3 次；仍失败则等待下一常规检查或手动检查。尚未公布按正常周期等待，不作为网络失败重试。

## 2. 来源与确定性校验

- 结构化候选来源为 `https://raw.githubusercontent.com/NateScarlet/holiday-cn/master/<公告年份>.json`。这是第三方整理的数据，不能标为政府提供的 JSON API；文件中的 `papers` 提供国务院公告地址。来源说明见 [holiday-cn](https://github.com/NateScarlet/holiday-cn)。
- 下载后校验公告年份、真实公历日期、节日名称、休息／上班标志、重复及冲突记录。404 或 papers／days 为空表示“尚未公布”，不得生成空年度文件、删除旧数据或猜测安排。
- 只访问候选中的 HTTPS `www.gov.cn`／`gov.cn` 公告链接，并逐次检查重定向目标；不执行远端代码，也不加载远端 JSON Schema。单次请求超时 30 秒、响应上限 1 MiB，失败有明确状态。
- 独立解析官方正文的标题年份、放假区间和调休上班日，展开并核对候选的每项休息／上班记录；联合节日、同月省略月份、农历／星期括注及跨年日期纳入解析用例。“与周末连休”的普通周末仍由既有周末逻辑判断。无法完整解析、天数不符、来源冲突或与候选不一致时禁止自动应用，显示原因。
- 不用模型推测节假日，不依据农历自行推断调休。已成功核对且候选内容未变化时可复用相同内容指纹的校验记录；内容变化必须重新核对。
- 公告年份与日期所属年份分开：下一年公告可能安排本年 12 月日期。按日期所属公历年写入年度 YAML；合并已保存的相邻公告贡献，只替换同一公告来源的旧贡献，不删除其他来源或其他年份资料。

## 3. 保存、冲突与刷新

- 继续使用 `HolidayYear { year, holidays, workdays }` 与 `holidays/<公历年份>.yaml`，不改变既有读者接口。自动任务和手动操作都经 AgendaService／HolidayService／Storage，不能旁路直接改文件。
- 在业务目录追加更新状态与已核对公告的记录，保存候选内容指纹、官方来源、公告年份、检查／成功时间、结果及各年度最后一次应用的原始文件哈希；不将来源或成功时间仅放在 YAML 注释里。
- 缺少年度文件时，校验通过后自动创建。自动管理的旧文件仅在当前原始字节哈希仍等于上次成功写入哈希时更新；先备份，再在锁内重新检查并原子替换。
- 原有未登记来源的年度文件不擅自接管：内容一致则报告无变化并保留原件；不同则保存已校验候选，标记本地冲突。自动管理的文件被手改后同样保留原件，包括注释与未知字段。
- 冲突页面显示日期／节日差异和官方来源。“保留本地”不写年度文件；“应用官方版本”须明确显示将替换所选年度资料，并在应用时核对候选哈希与本地文件哈希，过期则拒绝覆盖。其他年度不受该选择影响。
- 各年度独立提交，允许明确报告部分成功，不宣称多文件原子事务。只有成功写入且读回匹配才记成功；状态记录失败不得冒充完成。重启根据候选和文件哈希核对未完成记录，遇到新本地改动保守停止。
- 成功后立即失效 HolidayService 年缓存、递增业务数据版本并通知全部页面；客户端清理受影响日历缓存。只有检查／失败／无变化时不递增业务数据版本，不重写年度文件或产生重复备份。
- 缺少某年官方资料时，界面提示“该年法定放假安排尚未载入，当前仅按普通周末显示”，不能让普通周末判断暗示年度安排完整。

## 4. 设置与接口接缝

- 设置卡显示：自动更新开关、固定周期和时区、上次检查／成功、下一次检查、已有年份、各年状态、官方来源；提供“立即检查”及冲突处理。检查无变化时保持安静，仅更新状态；新增／更正成功、冲突及持续失败给出页面状态，不向会话反复投递提醒。
- 扩展 Desktop 适配方案中的 `update-settings`，允许修改 `holidayAutoUpdate`，继续使用设置修订检查并保留未保存草稿。
- 桥新增 `holiday-update-status`、`holiday-check-update`、`holiday-apply-candidate` 三个操作。检查操作不接受任意 URL 或文件路径；应用仅接受已经校验的候选身份、候选哈希、所选公历年份与预期本地哈希，不接受浏览器任意年度正文。
- 操作返回现有 op-result 信封，result 包含状态、各年结果与下次检查。状态区分 checking、updated、up-to-date、not-published、network-error、validation-failed、local-conflict、partial；业务失败沿用稳定错误码。自动与手动路径共用同一校验／保存实现，沿用 Desktop 可信来源限制。
- 原有 13 个 agenda_* 工具保持数量、名称与业务参数；本版不新增更新工具、提醒、重复事件或微信通知。

## 5. 验收

- 时间：10–1 月每日、2–9 月每月、跨年切换、首次挂载、关闭自动更新、退出后重新启动、休眠恢复、多个窗口／重复挂载及重试上限；离线样本固定时钟，不等待真实年度。
- 来源：已知 2025／2026 年公告与候选匹配；未公布空文件／404、HTML 冒充 JSON、错误年份、非法日期、冲突日期、联合节日、普通连休周末、跨年日期、公告格式变化、重定向越界、超时及过大响应。
- 数据：缺文件自动创建、无变化不写、原有资料保留、手改／注释／未知字段冲突、候选或本地哈希过期拒绝、备份与读回、部分成功、状态写失败及重启恢复；已有年度与无关 CSV／配置不变。
- 集成：设置保存冲突保留草稿，年度更新后所有打开页面的农历／休／班显示即时刷新；新增年份及更正日期正确，错误状态清楚，原生 Desktop 重启读回一致。
- 运行验证分开记录：离线类型／测试／构建、真实公开源读取与核对、隔离 Desktop 原生页面。网络不可达或未实施时不填写兼容通过，不把文档检查当作更新功能验收。

## 调研依据与当前限制

- 本轮已只读检查现有年度 YAML、缓存、存储接口与 Desktop 0.2.0-rc.2 的 Schedule 公共类型；通过网络读取了 2026 年国务院正文及 holiday-cn 候选字段。
- 2026 年公告成文于 2025-11-04，见 [政府转载原文](https://www.beijing.gov.cn/zhengce/zhengcefagui/202511/t20251104_4258873.html)。固定一年一天只查一次不能保证赶上公告。
- 检查时 2027 年候选 JSON 的 papers／days 为空；这是未公布样本，不是空的全年放假安排。Node 直连 GitHub raw 曾超时，政府原文 Node 读取成功；因此失败保留旧数据与手动重试必须纳入验收，不预先承诺所有网络可达。
- 本版只制定契约，没有新增源码、测试实现、运行配置、真实任务或安装操作。
